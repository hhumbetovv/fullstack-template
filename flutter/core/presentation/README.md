# Core Presentation

Houses the presentation runtime that generated view-models and feature widgets rely on. Import `package:core_presentation/exports.dart` to gain access to base classes, extensions, and widgets.

## Responsibilities
- **State management**: `StateNotifier` and `BaseViewModel` provide the mutation hooks, intent/effect streams, and logging used by generated and handwritten view-models.
- **Provider widgets**: Components such as `ViewModelProvider`, `ViewModelListener`, `StateBuilder`, and `StateSelector` connect view-model state to the widget tree (see common/presentation/README.md for global configuration hooks).
- **Use-case extensions**: Helpers on `UseCase`, `FlowUseCase`, and `PaginationUseCase` add logging, timing, and ergonomic `call()` methods so UI code can execute business logic succinctly.
- **Event bus**: Lightweight `EventBus` enables communication between view-models without tight coupling.
- **Utility widgets**: `BaseView`, `StatefulWrapper`, and other scaffolding elements wrap generated views with consistent behaviour.

## Typical consumers
- **Generated code from `gen_view_kit`** extends `_BaseViewModel`, instantiates `ViewModelProvider`, and calls the provided extensions.
- **Feature presentation modules** that implement custom view-models or views can also depend on these building blocks directly.
- **Domain adapters** use the use-case extensions to execute interactors with logging and crash reporting baked in.

## Getting started
1. Add `core_presentation` as a dependency.
2. Import the exports file: `import 'package:core_presentation/exports.dart';`.
3. Register dependencies (e.g. use cases) with your service locator so `useCase<T>()` can resolve them inside view-models.
4. Implement a view-model by extending `BaseViewModel` (or letting the generator create one) and override `initialState`.
5. Wrap screens in `ViewModelProvider` and respond to effects via `ViewModelListener` or generated effect hooks.

- `runWithLoading` toggles the generated `isLoading` flag when the state implements `LoadableState`.
- Intent/effect sealed classes are usually generated by `gen_view_kit`; custom implementations can follow the same pattern.

## How it fits with other core modules
- **Core Domain** supplies the use-case abstractions that view-models invoke through the provided extensions.
- **Core Data** implementations return `Result` objects consumed by `BaseViewModel` when updating UI state or posting messages.
- **Core Navigation** handles routing effects emitted by view-models, often via generated effect handlers.

## Notable APIs
- `useCase<T>()`: Resolves a use case from the service locator (`GetIt`).
- `BaseViewModel.postEffect`, `postIntent`, `postMessage`: Standard channels for communicating with the UI.
- `StateBuilder` / `StateSelector`: Widget adapters that rebuild when state changes or selectors produce new values.
- `EventBus.on<T>()` and `postEvent`: Decouple view-models needing cross-communication (e.g. broadcasting login events).

## Contributing tips
- Keep logging toggles (`logEvents`, `logState`, etc.) configurable so generated code can opt in/out per module.
- When introducing new lifecycle hooks or provider widgets, update generators so they leverage the new capabilities.
- Maintain zero Flutter UI in view-models; they should interact with the UI solely through effects, messages, and state updates.
- Document new utilities in this README so feature teams learn about them quickly.
